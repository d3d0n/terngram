# Сравнение с Telegram Desktop

Область сравнения — уже реализованные сценарии Terngram, а не обещание полного набора возможностей Telegram Desktop или полного соответствия Telegram API Terms. Проверены исходники Desktop (`dev`), дополнительный visibility-путь Web A (`master`) и установленный Telethon. Ссылки на ветки могут изменяться; ниже указаны конкретные функции. Исходники, тестовые сценарии и native protocol smoke не доказывают live MTProto или painted geometry Tern.

## Что действительно перенесено из desktop-подхода

1. **Идентичность операции важнее повторного вызова.** Точный random_id для send; точный max_id для read; media_id для изображений.
2. **Модель данных шире видимой страницы.** Полнота альбома проверяется серверным слоем перед bulk action.
3. **Поздний ответ не отменяет более новое состояние.** Ревизии истории, идентичность dialog snapshot, loader entries, account generation.
4. **Миниатюра не равна оригиналу.** Разделены автозагрузка preview и явное открытие full image.
5. **Отсутствие исключения и Bool-поле — не одно и то же.** MTProto readHistory Bool не интерпретируется как универсальный success flag.

## Непереносимое без расширения Tern

Web A [useMessageObservers](https://github.com/Ajaxy/telegram-tt/blob/master/src/components/middle/hooks/useMessageObservers.ts) читает maximum реально видимого нижнего message marker и исключает quick preview; [useBackgroundMode](https://github.com/Ajaxy/telegram-tt/blob/master/src/hooks/window/useBackgroundMode.ts) использует foreground focus. Desktop также имеет собственные scroll/window state.

Текущий TSP сообщает neither visible message IDs nor scroll offset; surface `visible` не равен pane focus и сейчас не передаётся компонентам backend. Для точной parity требуются события видимой границы истории и активности pane, а также поддержка освобождения media resources для ограниченного кеша. Эвристика recent input не объявляется лучшей этих сигналов.

Команды для проверки: `bun run check`, `bun run test`, `bun .smoke-client.ts`. Регрессионные сценарии перечислены в [ui.md](ui.md#тесты-runtime-proof-и-границы-доказательств). Проверка сети с полноценным Telegram-аккаунтом, финальная геометрия и удобство размеров в Tern не подменяются synthetic hello или mocked Telegram replies.

## Сетевая дисциплина и актуальность кеша

Дополнительно сопоставлены [InnerWidget::refreshFilterResults](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/dialogs/dialogs_inner_widget.cpp) (локальный IndexedList), [dialogs_widget search/cache](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/dialogs/dialogs_widget.cpp), [PeerData photo changes](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/data/data_peer.cpp), [ChannelData::setMembersCount](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/data/data_channel.cpp) и [Session::processUser/processChat](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/data/data_session.cpp).

По результатам исправлено:

- Поиск своих чатов больше не вызывает contacts.Search на каждый ввод. Фильтруется локальный каталог; оставшиеся страницы запрашиваются последовательно, параллельные открытия делят один запрос. Исчерпанный каталог не начинает пагинацию заново после refresh первой страницы.
- Metadata изменяется по конкретным peer updates: title применяется сразу, неизвестные поля становятся dirty. Full info имеет single-flight/version guard; собственные membership/admin/default-rights изменения инвалидируют права. Служебные сообщения слушаются через Raw, поскольку NewMessage не охватывает все MessageService.
- Наблюдаемый server retry-after обязателен: Flood/FloodPremium — метод, SlowMode — method+peer. Срок не укоротится от более позднего меньшего значения, сохраняется при замене worker; нет автоматического resend.
- Повторный просмотр уже разрешённого альбома не делает новый album RPC без invalidation. Смена чата снимает не начатые avatar/preview задачи; готовый/активный кеш сохраняется.
- Отмена/новый выбор фотографии имеет собственный intent: поздний старый ответ не открывает старый viewer. Открывается выбранный член альбома, не первый. Замена bytes сохраняет выбор по message identity.
- Фоновые удаления и пустой Escape не сбрасывают caret редактора. При утрате write permission фокус уходит из исчезнувшего editor; draft не отправляется и не теряется.
- ShortSentMessage для Saved Messages использует известный marked chat ID, а не невалидный cast InputPeerSelf→Peer.

Smoke проверяет эти сценарии через реальные native frames и изолированный worker. Это не обещание «FloodWait невозможен»: Telegram задаёт динамические лимиты, которые клиент должен соблюдать.

## Список прочитавших и маркер read N

[Desktop WhoReadExists / WhoReadIds](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/api/api_who_reacted.cpp) проверяет outgoing, уже прочитанное сообщение, обычную группу/megagroup, privacy/monoforum, runtime size threshold и expiry. Для группы вызывает [messages.getMessageReadParticipants](https://core.telegram.org/method/messages.getMessageReadParticipants) и использует возвращённый вектор.

Terngram повторяет эти ограничения и показывает его cardinality у выбранного своего сообщения. Запрос начинается после 300 мс устойчивого выбора; один message не обновляется чаще 30 секунд, server wait может увеличить срок. Нет массового запроса при рендере и нет polling. Типичный серверный предел — 100, но решает appConfig: граница включительная, fallback текущего Desktop при отсутствии значения — 50; expiry fallback — 7 дней. Неизвестное/просроченное/скрытое не считается нулём. Полный список имён в UI не добавлен: запрошен только числовой маркер.

### Честная идентификация соединения

В `terngram/telegram.py` `initConnection` получает `device_model="Desktop (<архитектура>)"`, `system_version` из фактической ОС (macOS version при доступности), `app_version="Terngram <installed package version>"`, `lang_code="en"` для текущего английского UI и двухбуквенный `system_lang_code` из locale процесса с fallback `en`. Это не имитация официального клиента: официальный `lang_pack` и чужой API ID не подставляются. Не включаются hostname, username, серийный номер или устойчивый аппаратный идентификатор. Имена/серийные номера нельзя добавлять для «лучшего device model». Эти метаданные не заменяют регистрацию собственного приложения.

[Получение API ID](https://core.telegram.org/api/obtaining_api_id#using-the-api-id) прямо предупреждает: аккаунты, входящие через неофициальные клиенты, автоматически наблюдаются; flooding/spam/накрутка counters ведут к бессрочному бану. Ни корректные метаданные, ни соблюдение retry-after, ни эта матрица не гарантируют отсутствия блокировки. Для ошибочного бана источник предлагает личное объяснение на recover@telegram.org, не автоматически сгенерированное письмо.

### Транспорт: какие проверки обязательны по 1.1

Источник: [MTProto Security Guidelines](https://core.telegram.org/mtproto/security_guidelines). Ответственность клиента сохраняется при использовании библиотеки. Проверять конкретный установленный и поставляемый исходник, не имя Telethon или диапазон версии:

| Проверка | Требование |
| --- | --- |
| DH prime/generator | `p` и `(p−1)/2` — простые, `2^2047 < p < 2^2048`; `g` допустим и удовлетворяет условиям residue из источника (`g=2`: `p mod 8=7`; `3`: `p mod 3=2`; `4`: без дополнительного условия; `5`: `p mod 5=1/4`; `6`: `p mod 24=19/23`; `7`: `p mod 7=3/5/6`). Можно кешировать проверенные пары/использовать проверенную таблицу, нельзя считать любые server values доверенными. |
| DH values/randomness | `1 < g,g_a,g_b < p−1`; рекомендован также safety interval `2^(2048−64)…p−2^(2048−64)` для `g_a/g_b`. Секретный exponent — CSPRNG; server entropy не заменяет локальную. |
| Key generation integrity | Проверить SHA1 расшифрованного `server_DH_inner_data` **без random padding**, все уже известные nonce/server_nonce/new_nonce. Последующая проверка DH-gen hash не заменяет inner SHA1. |
| Encrypted `msg_key` | Проверить SHA256-derived `msg_key` по расшифрованному plaintext **с padding** до использования результата; ошибки до этой проверки не дают иного наблюдаемого результата. |
| Length/padding | Объявленный length неотрицателен, кратен 4, не выходит за plaintext; remaining padding **12…1024 bytes**. Bounds-check отдельного BinaryReader не заменяет эти инварианты. |
| Session / IDs / replay / time | Session ID совпадает с активной сессией; outgoing msg_id чётный, incoming нечётный. Хранить последние N IDs; отвергать равный любому или **меньший всех** сохранённых, при переполнении удалять lowest. Это не запрет каждого ID ниже текущего maximum. Проверять окно +30/−300 секунд с указанными в источнике service/time-sync исключениями. |
| Mismatch | Некорректное сообщение полностью отбрасывается, его данные не используются; источник рекомендует закрыть/восстановить соединение. Исключение безопаснее продолжения с невалидными данными. |

**Результат независимой проверки конкретной зависимости:** установленная и locked Telethon **1.45.0** совпадают; на дату обзора это latest published release ([PyPI metadata](https://pypi.org/pypi/Telethon/json), [upstream tags](https://codeberg.org/Lonami/Telethon/tags)). В [v1.45.0 authenticator.py](https://codeberg.org/Lonami/Telethon/src/tag/v1.45.0/telethon/network/authenticator.py) отсутствуют safe-prime/generator validation и проверка SHA1 inner DH answer; в [v1.45.0 mtprotostate.py](https://codeberg.org/Lonami/Telethon/src/tag/v1.45.0/telethon/network/mtprotostate.py) — declared length/padding validation и полный replay-window control. Installed evidence: `.venv/lib/python3.14/site-packages/telethon/network/authenticator.py:112–157`, `network/mtprotostate.py:187–230`; версия — `uv.lock`/METADATA.

Replay-пробел точнее прежнего обзора: нет reject ниже **всех** retained IDs, eviction идёт в arrival order, `_highest_remote_id` может уменьшиться, из-за чего membership-check для более высокого уже сохранённого ID пропускается. Статический пример `[INFERENCE, не запускался]`: свежие odd same-session `A<C`, `A<B<C`, приём A,C,B, затем replay C может снова дойти до dispatch. Spec допускает B выше retained minimum — исправление не должно запрещать каждый ID ниже maximum.

CSPRNG, nonce comparisons, SHA256 msg_key, session ID, parity/time checks в изученном пути присутствуют, но не заменяют четыре пропущенных обязательных контроля. Это подтверждённые **control omissions**, не доказательство произвольного unauthenticated key compromise или физического buffer overread. Новейшая доступная версия сохраняет пробелы; простое обновление lower bound/relock не исправляет их. **Решение для выпуска:** реально исправленная upstream release либо явно поддерживаемый, reviewed dependency fork/replacement с декларацией/lock и malformed/replay regressions. Исправления библиотеки не внесены; site-packages не патчились.

**Воспроизведено офлайн интегратором:** synthetic packet передан реальному parser Telethon 1.45.0 с новым случайным ephemeral AuthKey, текущими session/msg_id/time, корректными SHA256 msg_key/AES и Pong body, но `declared_length=-4`. Наблюдаемый вывод: `offline synthetic packet: declared_length=-4; accepted_type=Pong`, exit 0. Это упражнение подтверждает отсутствие проверки отрицательной длины; не использует сеть, account/session data и не доказывает exploit против реального сервера. Это отдельное доказательство, не результат build/test gates и не runtime-проверка остальных трёх контролей.

### Поставленные typing и presence пути

`terngram/telegram.py`, `worker.py`, `ui/telegram.ts`, `ui/app.ts` и `ui/chat-dock.ts` теперь имеют законченный flow `select_peer`, `typing(chat_id,active)`, `activity()`. Реальный composer ввод отправляет `SendMessageTypingAction` без текста draft, throttle **4 секунды**, idle **5 секунд** → CancelAction; empty/send/edit/switch/logout/close отменяют при доступном транспорте. Draft restore не «печатает». Incoming User/Chat/Channel typing показывает sender/action активного чата, expires **6 секунд**, очищается cancel/message; own actions исключены.

User status переносит server `online.expires`/`offline.was_online`, грубые privacy states recently/last_week/last_month/unknown и `UpdateUserStatus`, без угадывания exact last-seen. Истёкший online становится unknown; транспорт отображается отдельно как `Telegram disconnected`. Own `account.updateStatus` использует keyboard/native/composer activity, refresh **55 секунд** при recent input, idle **60 секунд** → offline, best-effort offline при close/logout. Это наблюдаемая activity policy, **не точный host foreground**. Transient RPC соблюдают retry-after, без автоматического typing retry; ошибки не превращают send в успех. Подробная схема — [ui.md](ui.md#typing-и-telegram-user-presence). Источники: [setTyping](https://core.telegram.org/method/messages.setTyping), [account.updateStatus](https://core.telegram.org/method/account.updateStatus), [UserStatus](https://core.telegram.org/type/UserStatus). No-live/no-tests ограничения обзора сохраняются.

### TTL, чтение и обязательная совместимость

TTL сейчас **не реализован**. Нужны авторитетные `Message.date`/`ttl_period`, media-specific TTL/consumption lifecycle и chat policy `MessageActionSetMessagesTTL`, а не только отформатированное `time`. Срок должен применяться к history/live/edit/reconnect и уже просроченным ответам; по истечении удаляются body/media ID, preview/full cache и открытый viewer, а не только скрывается карточка. Проверить [Message](https://core.telegram.org/constructor/message), [messageActionSetMessagesTTL](https://core.telegram.org/constructor/messageActionSetMessagesTTL), [messages.readMessageContents](https://core.telegram.org/method/messages.readMessageContents) / [channels.readMessageContents](https://core.telegram.org/method/channels.readMessageContents) для content-read/view-once lifecycle. Не менять auto-delete policy без явного действия пользователя. Отсутствие blob-release гарантии — отдельный host/SDK пробел, не оправдание хранения истёкшего содержимого.

Для корректного auto-read нужны достоверные сведения об активности и прочитанной границе, включая wheel/trackpad. `requested/confirmed max_id` и отсутствие ghost mode уже полезны, но recent input и выбор чата не доказывают видимость. Не выдавать `reveal=end` за событие «отрисовано и прочитано». Конкретный viewport API не предписан Terms: нужны наблюдаемые факты либо другой достоверный путь. Явное действие чтения — честный пользовательский путь, но не доказательство автоматической desktop-parity. Outgoing receipts продолжают отражать сервер, не локальные догадки.

### Полный sponsored flow, который ещё требуется

Источник: [официальная спецификация sponsored messages](https://core.telegram.org/api/sponsored-messages). Ниже требования к flow, не поставленные функции. Для текущего доступа к каналам/bot chats применимы получение, показ и взаимодействия; fullscreen-video и global-search требования **условны**, пока соответствующих функций нет. Их отсутствие само по себе не нарушение ads-требований.

1. **Получение:** при открытии канала **или bot chat** `messages.getSponsoredMessages(peer)`, кеш результата на **5 минут**. Сохранять `messages`, `chats`, `users`, `posts_between`, `start_delay`, `between_delay`; передавать opaque `random_id: bytes` без потери (не числовой ID обычного сообщения). Схема ad: `title`, `message`+`entities`, `url`, `button_text`, optional `recommended`, `can_report`, `photo`, `media`, `color`, `sponsor_info`, `additional_info`, `min_display_duration`, `max_display_duration`. Поля/тайминги нельзя молча отбрасывать при мосте Python↔TS.
2. **Размещение:** канал — ниже всех posts, когда пользователь прокрутил **после последнего** сообщения; bot — action bar **над чатом**. Channel ad имеет title/text/media/button, “Recommended” вместо “Sponsored” при флаге, profile bubble `photo` и accent `color`. Bot title получает синий “Ad” либо “Recommended”, текст/entities, photo-thumbnail справа, accent при наличии. Sponsor info открывает обе переданные строки через menu item у channel ad / соответствующий info UI; ad не должна выглядеть обычным post.
3. **Открытие:** button/media/bar используют `url`; перед внешним URL требуется подтверждение, кроме hostname regex `(^|\.)(telegram\.(org|me|dog)|t\.me|te\.?legra\.ph|graph\.org|fragment\.com|telesco\.pe)$`. Разрешённые Telegram deep links открываются **в приложении**, не через браузер. Нужны распознавание ссылок, пользовательское согласие и реальное действие host, а не инертный label.
4. **View:** `messages.viewSponsoredMessage(random_id)` **только когда весь текст реально показан на экране** (button channel ad исключён). Создание native node, выбор чата, кеш/таймер или `reveal` не равны impression. Нужен достоверный факт показа; Terms не требуют конкретного viewport API, но текущая интеграция такого факта не получает.
5. **Click:** `messages.clickSponsoredMessage(random_id)` для link/button/bar/name/photo/mention; фото/беззвучное видео — `media=true` и URL; видео со звуком — `media=true` и fullscreen **без открытия URL**; клик по media в fullscreen — `media=true, fullscreen=true` и URL; fullscreen button — `fullscreen=true` и URL. Отдельный expand-video control не должен открыть URL.
6. **Report:** только при `can_report`, `messages.reportSponsoredMessage(random_id, option=b"")`; `ChooseOption` показывает server `title` и локализованные `text`/opaque `option`, повтор с выбранными bytes. Обработать `AdsHidden`, `Reported`, `AD_EXPIRED`, `PREMIUM_ACCOUNT_REQUIRED`; не имитировать report успех. На странице текст упоминает channel/bot ID, но показанная текущая TL-сигнатура содержит только `random_id`/`option`: сверять с фактическим layer/schema, не изобретать RPC-аргумент.
7. **Fullscreen channel video (при реализации player):** fetch с `msg_id`; first ad после `start_delay`, последующие через `between_delay` после скрытия, показывать в порядке, auto-hide через `max_display_duration`, manual hide только после `min_display_duration`. Все таймеры идут по playback time и останавливаются на pause. Смена видео того же канала внутри player не refetch и не сбрасывает таймеры. Сейчас video player отсутствует — это не уже поддержанный ads-flow.
8. **Global search (при реализации):** `contacts.getSponsoredPeers(q)` вместе с `contacts.search`; sponsored peers стоят между `my_results` и `results`, содержат sponsor info, отправляют view при фактической видимости, click без media/fullscreen flags, report по opaque `random_id`. Сейчас поиск палитры локальный, `contacts.search` отсутствует; не утверждать, что он уже требует или выполняет этот отдельный search-flow.

### Блокеры выпуска и предел доказательства

- **Прямые технические пробелы:** TTL/consumption/expiry и sponsored flow при уже доступных каналах/bot chats. Отсутствие полноценной feature parity требует оценки базовых сценариев по 1.3, а не утверждения, что обязательна каждая функция Telegram.
- **Наблюдаемость/хост:** отсутствие исходников Tern **не является нарушением Terms** и не требует миграции UI. В установленном Tern 0.3.0 и SDK доступен surface-level `visible` (backend его игнорирует), не видимость текста/IDs; `focus` — передача keyboard focus после node click, не активность pane. Нет подтверждённого contract для viewport/scroll-offset, top bot action bar, URL/deep-link routing или blob release. Это препятствия доказательству корректных read/impressions/placement/resource lifecycle, не самостоятельные юридические требования к конкретному API. Raw TSP reader/sender может подключить существующие события, но не создать отсутствующие host-возможности. Video player/global search не реализованы; их условные ads-flow не объявляются текущими нарушениями.
- **Где проверялся хост:** `/Applications/Tern.app` содержит executable/resources/Info.plist, но не исходники/protocol contract. SDK evidence: `node_modules/@oh-my-pi/pi-wire/src/tsp.ts`, `@oh-my-pi/pi-tui/src/native/backend.ts` и `native/blobs.ts`; локальные границы описаны в [tern-api.md](tern-api.md). Ordinary text/image/action nodes и outbound raw frames сами по себе не подтверждают host layout, playback/deep-link routing или освобождение bytes. Telethon 1.45 имеет Get/View/Click/ReportSponsoredMessageRequest, но наличие TL-schema не означает, что worker/frontend уже поддерживают ads.
- **Транспорт:** четыре подтверждённых mandatory-control пробела сохраняются в locked/latest Telethon 1.45.0. Нужен реально исправленный upstream artifact или решение о maintained reviewed dependency fork/replacement; нет доказанного version-only исправления, библиотека не изменена.
- **Внешние обязательства:** собственная регистрация API ID, реальные store descriptions/name/assets, сведения о монетизации и мониторинг developer account с 10-дневным remediation — требуют владельца продукта; данных в репозитории недостаточно.
- **Проверки:** обзор исходников не доказывает live межклиентскую совместимость, финальную отрисовку host или отсутствие бана. Эта запись не содержит утверждения «все тесты прошли» после последних изменений.

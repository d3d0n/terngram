# Security and Telegram API obligations

This document describes trust boundaries, observed controls, and open obligations—not a security certification, legal opinion, Telegram approval, or guarantee against account restrictions. **Full API Terms compliance has not been established.** In particular, channel access is implemented but official sponsored messages are not.

Implementation: [Telegram service](../terngram/telegram.py), [native binding](../terngram/tdlib.py), [worker](../terngram/worker.py), [application](../terngram/ui/app.ts). See [backend contracts](backend.md), [UI behavior](ui.md), [native host contract](tern-api.md), and [Desktop/Web comparisons](desktop-parity.md).

## Trust and data boundaries

- **Telegram and TDLib:** the current transport is Python calling the official native TDLib C JSON API. TDLib owns authorization, network reconnection, its database, files, and network outbox. There is no parallel legacy transport fallback. Secret chats are disabled.
- **Local account data:** the default directory is `$XDG_DATA_HOME/terngram` or `~/.local/share/terngram`, overridable with `--data-dir`. Credentials, drafts, active send intentions, Telegram database/authentication state, and downloaded media are sensitive. Directories use `0700`; application JSON and downloaded images use `0600`, owner/non-symlink checks, and atomic JSON replacement. The TDLib database encryption key is empty: permissions are **not encryption at rest** and do not protect against the same user, privileged processes, backups, or a compromised machine.
- **Local IPC and host:** credentials and the 2FA password cross the local worker JSONL channel; message text, images, and QR pixels reach the native Tern host. Masked input is a presentation feature, not isolation from process memory, IPC capture, screenshots, or host traces. Trust the machine, Python/Bun dependencies, TDLib binary, SDK, and host before signing in.
- **Git-plugin bootstrap:** `tern plugin install github.com/d3d0n/terngram` installs the repository's root manifest. First launch downloads the standalone runtime over HTTPS and checks the SHA256 pinned in `scripts/launch_release.sh` before extraction/execution. Downloads are staged in a private cache directory; failed downloads remove staging and the installation lock, and only a complete package becomes the cached runtime. Cached launches do not redownload or rehash installed files. Trust the installed Git revision and the local cache; this is not Developer ID signing, notarization, or protection against another process running as the same user. The cache contains runtime code, not account data.
- **Image paths:** downloads may be read only beneath `tdlib/files/**` or `tdlib/db/{profile_photos,thumbnails,secret_thumbnails,stickers,wallpapers,stories,photos}/**`. Every private path component is opened without following symlinks, with owner/type checks. Database/auth files and path escapes are not image sources. The database image exceptions follow TDLib [file types](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/telegram/files/FileType.cpp), [loader paths](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/telegram/files/FileLoaderUtils.cpp), and [global directories](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/telegram/Global.cpp).
- **Send storage:** active drafts/intents contain plaintext. Terminal outbox tombstones omit body, reply, and error; retention is bounded to 256 unreferenced terminal records, with persisted-pending/unresolved exceptions. Monotonic token allocation prevents reuse of retired IDs. This reduces retained content, not all metadata, and is not an exactly-once guarantee. See [backend](backend.md) for reconciliation and migration.

### Sessions and QR authentication

Login is QR-only, optionally followed by Telegram 2FA. There are no phone/code/email/signup forms. TDLib supplies and rotates the authoritative link; the application renders a temporary PNG and clears its QR node/secret fields on stage changes and shutdown. The app does not persist QR PNGs, login links, or plaintext 2FA passwords in its own state/logs.

**Native persistence is different:** TDLib's private binlog can retain unfinished QR authentication state/token for up to **5 minutes**, or password-stage state for up to **24 hours**. This is not plaintext password retention. The previously reviewed upstream [AuthManager.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/telegram/AuthManager.cpp) is the provenance for these lifetimes. Do not share the database because the UI no longer displays a QR.

A ready session is reused. Quit closes the app/worker but **does not revoke authorization**. Confirmed logout invokes TDLib logout and clears current application state; it is not a secure erase of backups, host memory, or preserved legacy personal files. “Use a different account” during unfinished password-stage login cancels that never-authorized login and starts a fresh QR flow; it is not a ready-session multi-account switcher.

### Safe diagnostics

Native TDLib logging is disabled (`logStreamEmpty`, verbosity `0`) **before client creation**. RPC errors are tied to their operation and use safe application codes/messages. Private `tdlib/last-error.json` contains only operation, root exception class, and up to 12 stack locations (basename/function/line), not exception values, arguments, locals, message text, tokens, or full paths. A diagnostic-write failure must not replace the original error.

For a report, share the operation, safe code, relevant stack locations, dependency versions, and sanitized reproduction steps. Never attach the account directory, raw RPC traces, QR screenshots, auth links, passwords, credentials, message content, or an unreviewed host capture. Offline fixtures and isolated temporary data are preferable to a real account. These controls cannot retroactively sanitize logs from other processes.

## Reads, presence, and protected media

Read requests preserve separate requested/confirmed maxima, single-flight per chat; failed RPCs do not advance frontend confirmation. Telegram read updates remain authoritative for the backend model and outgoing receipts. The UI's recent-input window and detached-history flag are heuristics: they do not establish painted message visibility, wheel/trackpad position, or active-pane focus. A `reveal=end` command is not proof that content was shown or read. There is no ghost-mode toggle.

Typing is sent for actual writable-chat composer edits, throttled at **4 seconds**, canceled after **5 seconds** idle or context changes; incoming actions expire after **6 seconds** and are not persisted. Own online follows observed input and a **60-second** idle deadline, with best-effort offline on close/logout. Privacy-filtered peer statuses are not replaced with invented exact last-seen; network connection is separate. This is not a host-foreground detector.

Content/deletion/ephemeral updates invalidate current media and stale overlays; version fences reject late downloads. Self-destruct/view-once previews return null without consuming content where applicable. Full open checks actual TDLib message/ephemeral save permissions and protected flags, calls `openMessageContent`, and rechecks the version. Non-saveable/protected content is not downloaded; unsupported restricted/age-verification/spoiler content returns `MEDIA_RESTRICTED`. Where protected self-destruct viewing is required, the result is `MEDIA_PROTECTED_VIEWER_REQUIRED`, not a claim that Telegram itself cannot display it.

These are implemented guards, **not a complete protected-viewer/resource lifecycle**. The installed SDK's native blob registry retains bytes without a release API; removing application cache entries or nodes does not prove host/SDK memory erasure. Host zoom and final geometry are host-owned. Surface-level `visible` exists in TSP but is not routed as message visibility or pane activity by the current integration; keyboard-focus routing is not foreground evidence. Required facts must come from trustworthy host signals or another reliable interaction design, not fabricated impressions. Terms do not mandate a particular viewport API or publication of Tern sources. See [native boundaries](tern-api.md).

## Telegram API Terms clause matrix

Requirements were reread on **2026-10-04**: [API Terms](https://core.telegram.org/api/terms), [API ID registration](https://core.telegram.org/api/obtaining_api_id), [sponsored messages](https://core.telegram.org/api/sponsored-messages), and [Content Licensing / AI Scraping](https://telegram.org/tos/content-licensing). They can change. “Observed” means an identified source path, not end-to-end certification. “External” requires product-owner evidence outside this checkout. No personal account or live Telegram operation was used for this documentation review.

| Clause and requirement | Observed implementation | Gap or required owner action |
| --- | --- | --- |
| **1.1 — protect privacy and follow [Security Guidelines](https://core.telegram.org/mtproto/security_guidelines)** | Private storage, safe diagnostics, image-path guards, content-free terminal tombstones; official native TDLib transport. | Plaintext active data/native auth persistence and host retention remain sensitive. Maintain binary provenance and review runtime/host/resource boundaries; permissions and an official engine do not establish full compliance. Qualified transport review follows below. |
| **1.2 — extensions must not violate Terms** | Local search, drafts, tracked sends, gallery, and reader count use standard Telegram operations. | Assess each extension against all applicable clauses; do not bypass TTL, reads, typing, or ads. Local send tokens do not remove native crash ambiguity. |
| **1.3 — basic features must work as expected across clients; recipients must not need this app** | Text/entities, reply, edit, forward, revoke-delete, history, receipts, and supported images use standard Telegram messages. | Other attachments and some service/topic scenarios are placeholders or unsupported; no secret chats. Evaluate basic interoperability with official clients. Missing every optional feature is not automatically a separate violation, but placeholders are not support. |
| **1.4 — no unconsented actions or interference with expiry, last-seen/online, reads, or typing** | User-directed sends/mutations, delete/logout confirmations, typing/status updates, permission checks and expiry invalidation; no ghost mode. | Reliable auto-read visibility and enforceable protected-viewer/retained-byte lifecycle remain unresolved. Input/connection heuristics do not prove actual foreground or reading. |
| **1.5 — Content Licensing and prohibition on AI/ML use of Telegram data** | Reviewed client paths contain ordinary messaging, not an AI/ML collection/training pipeline. | Absence of such code does not license external use. Source exceptions require **all relevant users** individually giving explicit, informed, affirmative, continued consent for specific content and chat/channel/non-global context; consent is non-transferable. An account-owner checkbox is insufficient. |
| **2.1 — obtain your own application API ID** | Credentials are validated and supplied to TDLib; official credentials are not substituted. | Entered credentials do not prove Terngram's own registration. Owner must register via [my.telegram.org/apps](https://my.telegram.org/apps) and use the application's own ID, not another app's or a sample. |
| **2.2 — prominently disclose Telegram API/ecosystem in store descriptions and any in-app intro** | Repository description and credentials introduction identify an unofficial Telegram API client and link API tools. | Verify the delivered intro and every actual store listing; checkout prose is not store evidence. |
| **2.3 — no “Telegram” in the app title unless preceded by “Unofficial”** | Package/CLI/surface use `terngram`; Telegram is descriptive text. | Verify external display/store names. Preserve Terngram, or apply the exact title exception if naming changes. |
| **2.4 — do not use the official Telegram logo** | Reviewed text/UI paths do not provide an official Telegram logo. | Inspect actual package/store icons and screenshots; unprovided assets are not certified by this review. |
| **3.1 — legitimate monetization is allowed** | No monetization mechanism was identified in reviewed client paths. | External payments/contracts are unknown. Any monetization must be legitimate; permission does not waive sponsored messages. |
| **3.2 — disclose every monetization method in every store description** | No observed paywall or first-party advertising. | Conditional on monetization: owner must disclose all methods in all actual listings and keep them current. |
| **3.3 — channel access requires official sponsored messages without interference** | Channels and bot chats are accessible. | **Open implementation gap:** no sponsored fetch/schema/render/view/click/report path. A text UI, lack of own monetization, or an individual Premium account does not waive the required support. Implement the applicable flow below. |
| **4.1 — Telegram notifies the responsible account of a breach** | Ordinary messages can be received; no operational monitoring evidence is supplied. | Owner must maintain an active responsible developer account/current registration details and monitor breach and Terms-change notices. No actual breach notice was observed. |
| **4.2 — fix notified issues within 10 days** | No observed notice or commenced deadline. | Establish an owner and remediation/release process. After notice, failure to fix within **10 days** can discontinue API access and lead to store-removal requests. Lack of a known notice is not proof of compliance. |

TDLib receives real device architecture/model, OS version, application version, system language, and API credentials—not an official-client disguise or official `lang_pack`. Connection metadata does not prove registration or privacy. The [API ID guidance](https://core.telegram.org/api/obtaining_api_id#using-the-api-id) warns that unofficial-client accounts are monitored and flooding, spam, or counter manipulation can cause permanent bans. Correct metadata/cooldowns do not guarantee freedom from restrictions. For an erroneous ban, that source requests a personal explanation to `recover@telegram.org`, not an automatically generated appeal.

### Sponsored flow that is still required

The following is an implementation requirement from the [official specification](https://core.telegram.org/api/sponsored-messages), **not shipped functionality**. Channel/bot retrieval, placement, and interactions apply to current access. Fullscreen-video and global-search extensions are conditional on implementing those features. TDLib exposing an API does not mean the worker/frontend support it; a TDLib bridge must preserve the equivalent semantics rather than invent raw RPC arguments.

1. **Fetch and preserve:** opening a channel **or bot chat** calls `messages.getSponsoredMessages(peer)` and caches its result for **5 minutes**. Preserve returned `messages`, `chats`, `users`, `posts_between`, `start_delay`, and `between_delay`. Ads carry opaque `random_id: bytes`, not ordinary numeric message IDs; preserve `title`, `message`/`entities`, `url`, `button_text`, and optional `recommended`, `can_report`, `photo`, `media`, `color`, `sponsor_info`, `additional_info`, `min_display_duration`, `max_display_duration` through the Python/TypeScript bridge.
2. **Placement and identity:** channel ads appear below all posts when the user scrolls past the last message, with title/text/media/button, “Sponsored” or “Recommended”, profile bubble when `photo` exists, and accent `color`. Bot ads appear **above the chat** as an action bar: blue “Ad” or “Recommended” title prefix, text/entities, right-side photo thumbnail, and supplied accent. They must not masquerade as ordinary messages. Expose both sponsor-information strings in the appropriate information UI; channel ads require a “Sponsor info” context-menu item.
3. **Navigation:** buttons/media/bars use `url`. Confirm external URLs unless the hostname matches `(^|\.)(telegram\.(org|me|dog)|t\.me|te\.?legra\.ph|graph\.org|fragment\.com|telesco\.pe)$`; allowed Telegram deep links open **in-app**, not through the browser. This requires real link routing, consent, and host action—not a decorative label.
4. **View:** call `messages.viewSponsoredMessage(random_id)` only when the **entire ad text is actually shown on screen**, excluding the channel button. Rendering a node, choosing a chat, starting a timer, caching, or issuing `reveal` is not an impression. The current integration cannot establish this fact.
5. **Click:** report link/button/bar/name/photo/mention interactions through `messages.clickSponsoredMessage`. Photo or silent-video media clicks set `media=true` and open the URL. Video with sound sets `media=true` and opens fullscreen **without opening the URL**; a fullscreen media click sets both `media=true, fullscreen=true` and opens the URL; its button sets `fullscreen=true`. A separate video-expand control must not open the URL.
6. **Report:** only when `can_report`; call `messages.reportSponsoredMessage(random_id, option=b"")`, show `ChooseOption` with server `title` and localized option text, then resend the selected opaque option bytes. Handle `AdsHidden`, `Reported`, `AD_EXPIRED`, and `PREMIUM_ACCOUNT_REQUIRED` honestly. The page's prose mentions a channel/bot ID, while its displayed TL signature contains only `random_id`/`option`: use the actual layer/schema, do not invent an argument.
7. **Fullscreen channel video, if implemented:** fetch with `msg_id`; display ads in order after `start_delay`, then `between_delay` after the previous ad hides. Auto-hide after `max_display_duration`; allow manual hide only after `min_display_duration`. Timers use playback time and pause with playback. Switching videos within the same channel's player neither refetches nor resets timers. **There is currently no video player**, so this is not an independently demonstrated current video-ads violation or supported flow.
8. **Global peer search, if implemented:** invoke `contacts.getSponsoredPeers(q)` with `contacts.search`; place sponsored peers between `my_results` and `results`, expose sponsor info, report real visible views, report clicks without media/fullscreen flags, and report using opaque `random_id`. **Current palette search is local**; it does not implement `contacts.search` or this conditional sponsored-search flow.

Open host questions include trustworthy visibility/activity, top bot action-bar placement, URL/deep-link routing, and releasable media resources. Installed SDK sources are `node_modules/@oh-my-pi/pi-wire/src/tsp.ts` and `node_modules/@oh-my-pi/pi-tui/src/native/{backend,blobs}.ts`. The previously inspected Tern 0.3.0 application bundle contained executable/resources/Info.plist, not host source or a complete protocol contract. Lack of Tern source availability is **not itself a Terms violation** and does not imply that UI migration is required.

## Qualified TDLib source review

The preserved review examined Homebrew cached source/receipt for **TDLib 1.8.67**, commit [`42e6a5259551178d1dab54a22ad96d14bd906e20`](https://github.com/tdlib/td/tree/42e6a5259551178d1dab54a22ad96d14bd906e20), **arm64 / clang / OpenSSL@4 4.0.3**. This documents that review's provenance, not a fresh full upstream audit. `uv.lock` pins Python dependencies, **not the native library**; moving Homebrew HEAD and a minimum/version check are not artifact pins. A distributed artifact needs its absolute library path, digest, source commit/build dependencies, and runtime version/commit linkage.

The prior integrator observed only a **no-login** ABI exercise: version/auth-initial/parse/close, including an awaited callback request. It did not exercise account authentication, malformed cryptographic packets, live delivery, or the whole engine. The requirements below come from [MTProto Security Guidelines](https://core.telegram.org/mtproto/security_guidelines); using official TDLib does not transfer away product responsibility.

| Security invariant | Required interpretation |
| --- | --- |
| DH prime/generator | `p` and `(p−1)/2` prime; `2^2047 < p < 2^2048`. Valid generators/residues: `g=2`: `p mod 8=7`; `3`: `p mod 3=2`; `4`: no extra condition; `5`: `p mod 5=1/4`; `6`: `p mod 24=19/23`; `7`: `p mod 7=3/5/6`. Verified pairs may be cached; arbitrary server values are not trusted. |
| DH values/randomness | `1 < g,g_a,g_b < p−1`; recommended stronger interval for `g_a/g_b`: `2^(2048−64)…p−2^(2048−64)`. Secret exponent uses local CSPRNG; server entropy is not a replacement. |
| Handshake integrity | Verify decrypted `server_DH_inner_data` SHA1 **without padding** and known nonce/server_nonce/new_nonce. Later DH-gen hash does not replace inner SHA1. |
| Encrypted integrity | Verify SHA256-derived `msg_key` over decrypted plaintext **including padding**, before using data; earlier parse errors must not expose a different result. |
| Length/padding | Declared length is nonnegative, divisible by four, and within plaintext; remaining padding is **12–1024 bytes**. Reader bounds alone do not prove this. |
| Session, replay, time | Active session ID; even outgoing/odd incoming IDs. Retain recent IDs, reject duplicates or IDs **below all retained IDs**, prune lowest on overflow—not every ID below the current maximum. Apply −300/+30-second freshness with specified service/time-sync exceptions. |
| Mismatch | Discard invalid messages completely without using their data; guidelines recommend closing/recreating the connection. |

### Observed upstream controls

- [DhHandshake.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/DhHandshake.cpp#L21-L124): prime/safe-prime, generator residues/cache, stronger `g_a/g_b` interval. [Handshake.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/Handshake.cpp#L171-L277): unpadded inner-answer SHA1, nonces, DH-gen hash.
- [Transport.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/Transport.cpp#L148-L298): decrypted `msg_key` comparison precedes body/length errors; mod-four, bounds, and padding checks. [AuthData.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/AuthData.cpp#L19-L45): unconditional sorted duplicate membership and pruning of lowest IDs. The historical legacy A,C,B,replay-C bypass does not recur in this control.
- [Random.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/tdutils/td/utils/Random.cpp#L33-L74): `RAND_bytes`, fatal on failure. [BigNum.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/tdutils/td/utils/BigNum.cpp#L244-L246): DH exponent uses `BN_rand`. Session/parity checks and dispatch gate appear in [AuthData.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/AuthData.cpp#L133-L164) and [SessionConnection.cpp](https://github.com/tdlib/td/blob/42e6a5259551178d1dab54a22ad96d14bd906e20/td/mtproto/SessionConnection.cpp#L733-L753).

### Residual static qualifications

1. **Low severity:** `Transport.cpp` excludes up to 15 transport-suffix bytes from decryption/hash, but computes `tail_size` from the original end; the checked padding length can include those unauthenticated bytes. **[INFERENCE, not executed]** an authenticated peer's encrypted header/body with no encrypted padding plus 12 transport bytes might pass the padding minimum. This is **not an unauthenticated exploit demonstration**.
2. **Informational:** rejection below all retained IDs starts after a 1000-record warmup. Before that, a unique fresh lower ID can be accepted; duplicate membership is always active.
3. **Informational:** the −300/+30 freshness predicate exists, but clock correction uses the same authenticated incoming ID before checking it, so it is not an independent future cutoff against the previous clock.

These are qualified source observations, not Telegram findings of Terms breach, demonstrated exploits, or predictions of bans. No malformed-TDLib-packet runtime test, live cryptographic interoperability check, or independent whole-engine audit was performed for this review. Neither “official TDLib guarantees compliance” nor “these observations automatically make TDLib noncompliant” is justified.

### Legacy-only history

The [legacy branch](https://github.com/d3d0n/terngram/tree/legacy) used Telethon 1.45.0. Its reviewed [authenticator](https://codeberg.org/Lonami/Telethon/src/tag/v1.45.0/telethon/network/authenticator.py) and [MTProto state](https://codeberg.org/Lonami/Telethon/src/tag/v1.45.0/telethon/network/mtprotostate.py) omitted safe-prime/generator, inner-DH SHA1, declared-length/padding, and replay-window controls. A prior offline synthetic packet with an ephemeral AuthKey, valid msg_key/AES, and `declared_length=-4` was accepted as Pong without an account/network. That historical evidence motivated the transport cutover; it **does not describe the current runtime, require site-packages patches, or demonstrate a TDLib exploit**.

## Change checklist

When changing auth, persistence, media, reads, or ads: preserve consent and server semantics; inspect every retained data boundary; keep diagnostics content-free; retain expiry/version fences; distinguish queued from confirmed and observed input from visibility. Reassess applicable Terms and the actual native artifact, not just dependency versions. Owner evidence is still needed for API registration, shipped names/assets/listings, monetization, and developer-account notice/remediation handling. Source review and offline protocol evidence cannot establish live interoperability, final host rendering, or freedom from bans.
